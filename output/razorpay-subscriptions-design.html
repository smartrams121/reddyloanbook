Database Schema Changes

New Model: SubscriptionPlan

Plans created by Platform Admin (Monthly, Yearly, Custom)

model SubscriptionPlan {
  id                String   @id @default(cuid())
  name              String                  // "Monthly Basic", "Yearly Pro"
  amountPaise       Int                     // 50000 = ₹500
  intervalUnit      String                  // "monthly" | "yearly"
  intervalCount     Int      @default(1)    // 1 = every 1 month/year
  description       String?
  razorpayPlanId    String?  @unique        // Razorpay plan_xxxxx
  isActive          Boolean  @default(true)
  createdAt         DateTime @default(now())
  updatedAt         DateTime @updatedAt

  subscriptions     Subscription[]
}

New Model: Subscription

One per Owner — their subscription lifecycle

model Subscription {
  id                    String    @id @default(cuid())
  ownerId               String    @unique     // One subscription per owner
  owner                 User      @relation(fields: [ownerId], references: [id])

  planId                String?
  plan                  SubscriptionPlan? @relation(fields: [planId], references: [id])

  status                String    @default("TRIAL")
  // TRIAL | ACTIVE | EXPIRING | PAST_DUE | SUSPENDED | CANCELLED

  // Trial tracking (managed by us, NOT Razorpay)
  trialStartDate        DateTime  @default(now())
  trialEndDate          DateTime              // Set on creation (approval date + trial days)
  trialDays             Int       @default(30)

  // Subscription dates
  currentPeriodStart    DateTime?
  currentPeriodEnd      DateTime?

  // Razorpay references
  razorpaySubscriptionId  String?  @unique   // sub_xxxxx (created when first payment made)
  razorpayCustomerId      String?            // cust_xxxxx

  // Admin actions
  suspendedAt           DateTime?
  suspendedReason       String?
  cancelledAt           DateTime?
  lastPaymentAt         DateTime?
  nextPaymentDue        DateTime?

  // Metadata
  notes                 String?              // Admin notes
  createdAt             DateTime  @default(now())
  updatedAt             DateTime  @updatedAt

  payments              SubscriptionPayment[]

  @@index([ownerId])
  @@index([status])
}

New Model: SubscriptionPayment

Every payment attempt — success or failure

model SubscriptionPayment {
  id                    String    @id @default(cuid())
  subscriptionId        String
  subscription          Subscription @relation(fields: [subscriptionId], references: [id])

  amountPaise           Int
  status                String    // "SUCCESS" | "FAILED" | "PENDING" | "REFUNDED"
  method                String?   // "upi" | "card" | "netbanking" | "wallet"

  // Razorpay references
  razorpayPaymentId     String?   @unique   // pay_xxxxx
  razorpayOrderId       String?             // order_xxxxx
  razorpaySignature     String?

  // Period this payment covers
  periodStart           DateTime?
  periodEnd             DateTime?

  // Fee (snapshot at payment time — one number covers all taxes)
  effectiveRate         Float?              // Total deduction % (e.g. 2.36). From PlatformSetting.
  feeAmountPaise        Int?                // Total deducted (e.g. 23600 = ₹236)
  netAmountPaise        Int?                // You receive (amountPaise - feeAmountPaise)

  // Invoice + Settlement
  invoiceNumber         String?   @unique   // INV-2026-0001
  settledAt             DateTime?           // When bank credit confirmed (admin marks)
  settledBy             String?             // Admin who confirmed settlement

  paidAt                DateTime?
  failureReason         String?
  createdAt             DateTime  @default(now())

  @@index([subscriptionId])
  @@index([status])
}

Design Note: Why Trial in Our DB?

Razorpay Subscriptions has a trial_period field, but it's set at the plan level and can't be customized per-subscriber. Since Platform Admin needs to set 30-day, 90-day, or 6-month trials per owner (sales offers), we manage trials entirely in our DB. Razorpay only enters when actual payment happens.

Key API: Create Order (Payment Flow)

// POST /api/subscription/create-order
// Called when Owner clicks "Pay Now"

const razorpay = new Razorpay({ key_id, key_secret })

// 1. Get owner's subscription + plan
const sub = await prisma.subscription.findUnique({
  where: { ownerId: user.id },
  include: { plan: true }
})

// 2. Create Razorpay order
const order = await razorpay.orders.create({
  amount: sub.plan.amountPaise,      // e.g. 1000000 = ₹10,000
  currency: 'INR',
  receipt: `sub_${sub.id}_${Date.now()}`,
  notes: {
    subscriptionId: sub.id,
    ownerId: user.id,
    planName: sub.plan.name
  }
})

// 3. Record pending payment
await prisma.subscriptionPayment.create({
  data: {
    subscriptionId: sub.id,
    amountPaise: sub.plan.amountPaise,
    status: 'PENDING',
    razorpayOrderId: order.id,
    periodStart: sub.currentPeriodEnd || new Date(),
    periodEnd: addMonths(sub.currentPeriodEnd || new Date(),
                         sub.plan.intervalCount),
  }
})

return { orderId: order.id, amount: sub.plan.amountPaise }

Key API: Verify Payment

// POST /api/subscription/verify-payment
// Called after Razorpay checkout success callback

// 1. Verify signature (CRITICAL — prevents tampering)
const expectedSig = crypto.createHmac('sha256', RAZORPAY_KEY_SECRET)
  .update(orderId + '|' + paymentId)
  .digest('hex')

if (expectedSig !== signature) → 400 Invalid signature

// 2. Update payment record
await prisma.subscriptionPayment.update({
  where: { razorpayOrderId: orderId },
  data: {
    status: 'SUCCESS',
    razorpayPaymentId: paymentId,
    razorpaySignature: signature,
    method: paymentDetails.method,   // "upi", "card", etc.
    paidAt: new Date()
  }
})

// 3. Activate subscription
const payment = await prisma.subscriptionPayment.findUnique(...)
await prisma.subscription.update({
  where: { id: payment.subscriptionId },
  data: {
    status: 'ACTIVE',
    currentPeriodStart: payment.periodStart,
    currentPeriodEnd: payment.periodEnd,
    lastPaymentAt: new Date(),
    nextPaymentDue: payment.periodEnd,
    suspendedAt: null,
    suspendedReason: null,
  }
})

Middleware: Subscription Gate

// In src/middleware.ts — added check for owner access

if (user.role === 'OWNER' && !isPublicPath && !isPaymentPath) {
  const sub = await getOwnerSubscription(user.id)  // cached

  if (sub.status === 'SUSPENDED') {
    // Redirect to payment page — can't use app
    return NextResponse.redirect('/payment')
  }

  if (sub.status === 'TRIAL' && isPastDate(sub.trialEndDate)) {
    // Trial expired — suspend and redirect
    await suspendSubscription(sub.id, 'Trial expired')
    return NextResponse.redirect('/payment')
  }
}

End-to-End Flows

Flow 1: Registration → Trial

1
Owner registers
Fills registration form (name, phone, email, city, org name). Status: PENDING.
2
Platform Admin reviews
Sees registration request. Selects trial period (30/90/180/custom days). Optionally assigns a plan.
3
Approve → Create Owner + Subscription
Transaction: create User (OWNER), create Subscription (status=TRIAL, trialEndDate=now+trialDays). No Razorpay call yet.
4
Owner logs in
Full app access. Sidebar shows "Subscription" with trial badge. No popups until 30 days before expiry.

Flow 2: Trial → Payment (Early or At Expiry)

1
Owner visits /payment (or popup redirects)
Sees trial status + available plans. If within 30 days of expiry, popup appears on dashboard after login.
2
Selects plan + clicks "Pay Now"
Client calls POST /api/subscription/create-order. Server creates Razorpay order. Returns orderId.
3
Razorpay checkout opens
checkout.js modal shows UPI / Card / Net Banking options. Owner completes payment.
4
Success callback → Verify
Client sends paymentId + orderId + signature to POST /api/subscription/verify-payment. Server verifies HMAC signature.
5
Activate subscription
Status → ACTIVE. Period start = now (or trial end, whichever is later). Period end = start + plan interval. Owner redirected to dashboard.
6
Webhook confirms (backup)
Razorpay sends payment.captured webhook. Idempotent handler ensures activation even if client callback failed.

Flow 3: Renewal

1
30 days before currentPeriodEnd
Status changes to EXPIRING (via daily cron job). Popup appears on owner dashboard.
2
Owner pays
Same flow as initial payment. Period extends from current end date (no gap).
3
If owner doesn't pay by expiry
Daily cron: if currentPeriodEnd < today and status=EXPIRING → set status=SUSPENDED. Owner can only see payment page.
4
Late payment (after suspension)
Owner pays from suspended payment page. New period starts from payment date (no credit for suspended days). Instant reactivation.

Flow 4: Admin Extends Trial

1
Admin clicks "Extend" on subscription
Modal: "Extend trial by ___ days". Reason field (optional). Confirm.
2
API updates trialEndDate
trialEndDate += extensionDays. If was EXPIRING/SUSPENDED, status reverts to TRIAL. Audit logged.
3
Owner sees updated trial
Next login shows extended date. Popup disappears if now > 30 days from new end date.

Flow 5: Offline / Cash Payment

1
Owner pays via bank transfer / cash
Not through Razorpay. Owner informs Platform Admin.
2
Admin clicks "Activate" on subscription
Selects plan + payment period. Creates SubscriptionPayment record with status=SUCCESS, method="offline".
3
Subscription activated
Status → ACTIVE. Dates set. No Razorpay involvement. Audit logged with admin who activated.

// Added to cleanup.sh or new subscription-check.sh (runs daily)

How Reconciliation Works

1
Owner pays via Razorpay
Payment recorded in our DB with razorpayPaymentId. Status: SUCCESS. Settled: Pending.
2
Razorpay settles to your bank (T+2 business days)
Razorpay sends the amount minus 2.36% fee to your linked bank account. You can also check in Razorpay Dashboard → Settlements.
3
Admin verifies in bank statement
Check bank account for Razorpay credit. Amount matches "You Get" column.
4
Mark as Settled in our app
Click "Pending" badge → confirms settlement. Records who confirmed and when. Settlement date stored.

Requirement Mapping

All 7 original requirements and how they're handled:

1
Sales team gives custom trial (e.g., 6 months free, then ₹10,000/year)
Platform Admin sets trialDays at registration approval (30/90/180/custom). Plan assigned separately — can be assigned at approval or later. Trial managed in our DB, not Razorpay.
2
No popups during trial until 30 days before expiry
Client-side check: if (daysUntilExpiry <= 30 && !sessionStorage.dismissed). Popup on owner dashboard only. "Remind me later" dismisses for the session. Payment page always accessible via sidebar for early payment.
3
Owner can pay early during trial
Payment page (/payment) accessible anytime via sidebar. Shows available plans with "Pay Now". On payment: status changes to ACTIVE, period starts from trial end date (gets full paid period, trial days not wasted).
4
Immediate activation on payment
POST /api/subscription/verify-payment sets status=ACTIVE in the same request. Owner redirected to dashboard immediately. Razorpay webhook is backup (idempotent).
5
Bank settlement (T+2) — when does money reach admin?
Razorpay settles to linked bank account in T+2 business days. Our system activates immediately on payment capture (doesn't wait for settlement). Platform Admin can check settlement status in Razorpay dashboard.
6
Rate change for existing subscribers
Admin "Change Plan" action updates the plan on the subscription. Current period is honored — new price applies only at next renewal. Owner sees updated plan on their payment page.
7
Suspended account — renewal date logic
Suspended owner pays → new period starts from payment date (not original expiry). No credit for suspended days. This prevents gaming (suspend for 6 months, pay, get backdated period). Admin can override via "Activate" with custom dates if needed.

Priority 2 — Build When 25+ Owners

🏷️ Coupon / Discount Codes

Promotional pricing for sales team to offer.

  • Coupon model: code, discount type (% or flat), max uses, valid dates
  • Usage: Owner enters code on payment page → discounted price
  • Example: "DIWALI50" = 50% off first payment. "REFER500" = ₹500 off
  • Admin: Create/deactivate coupons, see usage count, revenue impact
🤝 Referral Program

Owner refers another owner → both get benefit.

  • Each owner gets a unique referral code
  • New owner enters code at registration
  • On first payment: referrer gets 1 month free extension, new owner gets ₹500 off
  • Admin dashboard: referral tree, top referrers, total revenue from referrals
📢 Broadcast Announcements

Send targeted messages to owners.

  • In-app notifications: Bell icon with unread count (different from system banner)
  • Target: All owners, trial only, active only, expiring only, by city
  • Content: New feature announcements, maintenance windows, festival offers
  • History: Admin sees sent messages + read receipts

Priority 3 — Build When 50+ Owners

🛡️ Platform Health Monitor

Admin dashboard for system health (currently only via SSH).

  • Server stats: CPU, RAM, disk usage (read from monitoring API)
  • App stats: Active sessions, API response times, error rate
  • DB stats: Total records, DB size, slow queries
  • Uptime: Last downtime, current streak, response time graph
  • Alerts: In-app notification when server metrics cross thresholds
🎫 Support Tickets

In-app support system replacing WhatsApp/call support.

  • Owner: Create ticket from Help page (category, description, screenshot)
  • Admin: Ticket queue with status (Open/In Progress/Resolved), priority, SLA timer
  • Chat thread: Messages between admin ↔ owner on each ticket
  • Metrics: Average resolution time, tickets per owner, common issues
